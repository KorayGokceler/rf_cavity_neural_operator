# Adaptive mesh refinement in production FE codes for EM eigenmode (cavity) problems

Scope and method. Open-source codes (Palace, MFEM, NGSolve/Netgen) were read from source: shallow clones of the default branch taken on 2026-10-25/26 (Palace `8bd206f`, Palace release 0.18.1 of 2026-09-21 is the latest tag in CHANGELOG; MFEM `30bf1c9`; NGSolve `d242b9b`; Netgen `4cd1365`). deal.II is from the 9.7.0 doxygen. Commercial codes (HFSS, CST, COMSOL) are from vendor help pages, vendor training material, and vendor-API wrappers. Several vendor pages were unreachable (503/403), so some defaults below are second-hand; each one is flagged. "Inference" means my own reading, not a source statement.

## 1. AWS Palace: eigenmode AMR (estimator, Dörfler fraction, Tol / MaxIts / MaxSize, nonconformal, stop rule)

### Takeaway
Palace stops on an **estimator threshold**, not on the change between passes. It runs while `err >= Tol` (default 1e-2), stops after `MaxIts` passes (default 0, so AMR is off unless set) or once DOFs exceed `MaxSize` (default 0, no limit). Marking is Dörfler with `UpdateFraction` = 0.7. Refinement is nonconformal by default (`MaxNCLevels` = 1). For eigenmodes, the per-element indicator is the RMS over the requested modes of an energy-normalised ZZ flux-recovery estimator. There is no minimum pass count, no consecutive-pass test and no minimum-growth guard.

- Several modes. For each eigenpair `i < num_requested`, the eigensolver computes B = −(1/iω) curl E and calls `estimator.AddErrorIndicator(E, B, total_domain_energy, indicator)`. — [palace/drivers/eigensolver.cpp L555-581](https://github.com/awslabs/palace/blob/8bd206f7e10e5a2ec93a2483514894d14c8a5102/palace/drivers/eigensolver.cpp#L555-L581). - Conformity: "Nonconformal refinement is supported for all mesh types, and additionally conformal refinement is supported for simplex meshes. AMR is available for all problem types apart from driven problems in the time domain." — [docs/src/guide/model.md L39-53](https://github.com/awslabs/palace/blob/8bd206f7e10e5a2ec93a2483514894d14c8a5102/docs/src/guide/model.md)
- Curved geometry. Refinement goes through MFEM's `GeneralRefinement`. ### Inferences
- `Tol` is an absolute bound on an energy-normalised estimator, so it is dimensionless and roughly a relative field error, not an eigenvalue error. 1e-2 on the field corresponds to an eigenvalue error of order 1e-4, since the eigenvalue error scales with the square of the energy-norm error. This scaling is standard theory, not a Palace statement.
- With Dörfler θ = 0.7 and h-bisection, every pass refines at least one element, so the mesh always grows. Palace still has no "consecutive converged passes" logic. A single pass whose estimator falls below `Tol` stops the run.
- Curvature after refinement is the interpolated parent curvature. MFEM does not re-project to CAD, so the geometric error stays fixed at the input mesh's geometric resolution. This holds even when the local h shrinks (inferred from the MFEM code path; Palace does not document it).

### Gaps
- The rendered config page (`awslabs.github.io/palace/stable/config/model/`) returned 404 at fetch time, so the schema/struct source was used instead. The values match each other.
- No Palace documentation gives a recommended `Tol` for cavity eigenmodes. The transmon example only states `MaxIts` (value printed at doc build time, not read).

## 2. MFEM: ThresholdRefiner, ZZ / L2-ZZ / Kelly estimators for H(curl), nonconforming refinement, ex13

### Takeaway
MFEM's `ThresholdRefiner` is threshold-based. It marks elements with `local_err > max(total_fraction * total_err, local_err_goal)`. The default is the max-norm with fraction 1/2, so it marks elements above half the largest error. It stops when `total_err <= total_err_goal` (default 0), when no element is marked, or when `num_elements >= max_elements`. The ZZ estimators accept `CurlCurlIntegrator`, so they work for H(curl), and the Tesla miniapp uses this. Kelly is documented as scalar-diffusion only. The Maxwell eigenvalue example ex13p has **no AMR**: it uses uniform refinement only.

### Cited Findings
- `ThresholdRefiner` doc: "uses the given ErrorEstimator to estimate local element errors and then marks for refinement all elements i such that loc_err_i > threshold." Setters: `SetTotalErrorNormP` (default ∞), `SetTotalErrorGoal` ("stop when total_err <= total_err_goal. The default value is zero."), `SetTotalErrorFraction` ("The default value is 1/2."), `SetLocalErrorGoal` ("stop when local_err_i <= local_err_goal. The default value is zero."), `SetMaxElements` (default LONG_MAX), `SetNCLimit` ("maximum ratio of refinement levels of adjacent elements (0 = unlimited)"), `PreferNonconformingRefinement`, `PreferConformingRefinement` ("Use conforming refinement, if possible (triangles, tetrahedra) -- this is the default."). — [mfem mesh/mesh_operators.hpp](https://github.com/mfem/mfem/blob/master/mesh/mesh_operators.hpp)
- Constructor defaults: `total_norm_p = infinity()`, `total_err_goal = 0.0`, `total_fraction = 0.5`, `local_err_goal = 0.0`, `max_elements = numeric_limits<long long>::max()`, `non_conforming = -1`, `nc_limit = 0`. Threshold = `max(total_err * total_fraction * pow(num_elements, -1.0/total_norm_p), local_err_goal)` for finite p, else `max(total_err * total_fraction, local_err_goal)`. STOP is returned if `num_elements >= max_elements`, if `total_err <= total_err_goal`, or if `num_marked_elements == 0`. — [mfem mesh/mesh_operators.cpp](https://github.com/mfem/mfem/blob/master/mesh/mesh_operators.cpp)
- ZZ estimators. `ZienkiewiczZhuEstimator` takes any integrator implementing `ComputeElementFlux()`/`ComputeFluxEnergy()`. `SetFluxAveraging(0)` (default) averages across attribute interfaces. `L2ZienkiewiczZhuEstimator` replaces averaging "by a global L2 projection (requiring a mass matrix solve)", is "Implemented for the parallel case only", and has "Local L_p norm to use, default is 1". `KellyErrorEstimator` "provides a fast error indication strategy for smooth scalar parallel problems … appropriate only for problems with scalar diffusion coefficients (e.g. Poisson problems)"; it omits the constant C and "ignores boundary faces". — [mfem fem/estimators.hpp](https://github.com/mfem/mfem/blob/master/fem/estimators.hpp)
- `CurlCurlIntegrator` overrides `ComputeElementFlux` and `ComputeFluxEnergy`, so it can drive ZZ on Nédélec spaces. — [mfem fem/bilininteg.hpp ~L2963 @30bf1c9](https://github.com/mfem/mfem/blob/30bf1c91e1909a600d66f1194b4a326a724e653d/fem/bilininteg.hpp)
- H(curl) AMR in practice (Tesla magnetostatics miniapp). `GetErrorEstimates` uses `CurlCurlIntegrator`, a flux space `RT_FECollection(order_-1)`, a smoothed flux space `ND_FECollection(order_)` and `norm_p = 1` in `L2ZZErrorEstimator`. The loop marks elements with error above `frac = 0.5` of the global maximum (`pmesh.RefineByError(errors, threshold)`). It stops at `maxit` (default 100, `-maxit`) or when the ND problem size exceeds `max_dofs = 10000000`. — [miniapps/electromagnetics/tesla.cpp L117, L269-348](https://github.com/mfem/mfem/blob/30bf1c91e1909a600d66f1194b4a326a724e653d/miniapps/electromagnetics/tesla.cpp#L269-L348); [tesla_solver.cpp L405-423](https://github.com/mfem/mfem/blob/30bf1c91e1909a600d66f1194b4a326a724e653d/miniapps/electromagnetics/tesla_solver.cpp#L405-L423)
- Reference AMR example ex6p (Poisson). `L2ZienkiewiczZhuEstimator` with an RT smoothed-flux space ("this is the default") "to better handle hanging nodes and parallel partitioning". `ThresholdRefiner refiner(estimator); refiner.SetTotalErrorFraction(0.7);`. The comment says "refine elements with errors larger than a fraction of the maximum element error". It stops on `global_dofs >= max_dofs` (default `max_dofs = 100000`) or on `refiner.Stop()`. It has an optional alternating h/p mode (`-pref`) and conforming or nonconforming refinement. — [examples/ex6p.cpp L32-48, L75, L254-381](https://github.com/mfem/mfem/blob/30bf1c91e1909a600d66f1194b4a326a724e653d/examples/ex6p.cpp)
- ex13p (Maxwell eigenproblem with AME/LOBPCG) refines the mesh only uniformly: "-rs"/"-rp" give "Number of times to refine the mesh uniformly in serial/parallel". There is no estimator or refiner in the file. — [examples/ex13p.cpp L65-127](https://github.com/mfem/mfem/blob/30bf1c91e1909a600d66f1194b4a326a724e653d/examples/ex13p.cpp)
- Curved meshes: after refinement `Mesh::UpdateNodes()` runs `Nodes->FESpace()->Update(); Nodes->Update(); SetVerticesFromNodes(Nodes);`, so children inherit the interpolated parent geometry. — [mesh/mesh.cpp L10208-10221](https://github.com/mfem/mfem/blob/30bf1c91e1909a600d66f1194b4a326a724e653d/mesh/mesh.cpp#L10208-L10221)

### Inferences
- MFEM leaves the stop rule to the application. `ThresholdRefiner` only knows about estimator goals and element caps. Neither the examples nor the miniapps stop on an eigenvalue change between passes.
- With the default max-norm threshold, at least the max-error element is always marked while `total_err > 0`, so a pass always grows the mesh. The `num_marked == 0` STOP can only fire when `local_err_goal` or `total_fraction ≥ 1` excludes all elements.

### Gaps
- No MFEM example combines AMR with an eigenvalue solve (ex11/ex13 are uniform-only), so MFEM has no documented multi-mode marking rule.

## 3. NGSolve / Netgen: mesh.Refine (marked bisection), mesh.Curve after refinement, ZZ tutorial, Maxwell EVP, RefineHP

### Takeaway
NGSolve gives you primitives, not an AMR driver. `mesh.SetRefinementFlag` plus `mesh.Refine()` runs marked-edge tetrahedral bisection. New boundary points are projected onto the CAD geometry (`PointBetween`). **If the mesh was curved, Netgen rebuilds the curved elements at the same order automatically after `Refine`**, so the user does not have to call `Curve` again. The official tutorials use a ZZ-type flux-recovery estimator, mark at `0.25 * max(eta2)`, and stop on an ndof budget (`while fes.ndof < 50000`). They have no estimator tolerance and no eigenvalue-change test. The Maxwell eigenvalue tutorial uses a priori geometric `RefineHP(levels=2, factor=0.2)` toward marked edges, not adaptive refinement.

### Cited Findings
- `Mesh.Refine(mark_surface_elements=False, onlyonce=False)`: "Local mesh refinement based on marked elements, uses element-bisection algorithm". `RefineUniform`: "splitting trigs into 4, and tets into 8". `RefineHP(levels, factor=0.125)`: "Geometric mesh refinement towards marked vertices and edges, uses factor for placement of new points". `SetRefinementFlag(ei, refine)` / `SetRefinementFlags(list)`. `Curve(order)`: "Curve the mesh elements for geometry approximation of given order". — [ngsolve comp/python_comp_mesh.cpp L864-966 @d242b9b](https://github.com/NGSolve/ngsolve/blob/d242b9b4bbad5617676171d8daf58e13d64fb1ad/comp/python_comp_mesh.cpp#L864-L966)
- `MeshAccess::Refine(onlyonce)` calls `mesh.Refine(NG_REFINE_H, onlyonce)`, then `UpdateBuffers()` and `updateSignal.Emit()`. — [ngsolve comp/meshaccess.cpp L2130-2137](https://github.com/NGSolve/ngsolve/blob/d242b9b4bbad5617676171d8daf58e13d64fb1ad/comp/meshaccess.cpp#L2130-L2137)
- Netgen `Ngx_Mesh::Refine` runs `mesh->GetGeometry()->GetRefinement().Bisect(*mesh, biopt)`, then `if(mesh->GetCurvedElements().IsHighOrder()) mesh->GetCurvedElements().BuildCurvedElements(&mesh->GetGeometry()->GetRefinement(), mesh->GetCurvedElements().GetOrder());`. So curvature is regenerated at the previous order on the refined mesh. — [netgen libsrc/interface/nginterface_v2.cpp L1114-1135 @4cd1365](https://github.com/NGSolve/netgen/blob/4cd13652d00bd5ac889c19b34dc0ed630c6fb0f7/libsrc/interface/nginterface_v2.cpp#L1114-L1135)
- In the bisection, new midpoints on boundary edges and faces come from `geo.PointBetween(...)` / `geo.PointBetweenEdge(...)`, i.e. they are projected onto the geometry. The file references the Arnold-Mukherjee marked-edge algorithm. `Bisect` has an optional `quality_loss` output. — [netgen libsrc/meshing/bisect.cpp L55, L3527-3648](https://github.com/NGSolve/netgen/blob/4cd13652d00bd5ac889c19b34dc0ed630c6fb0f7/libsrc/meshing/bisect.cpp); [bisect.hpp L11-55](https://github.com/NGSolve/netgen/blob/4cd13652d00bd5ac889c19b34dc0ed630c6fb0f7/libsrc/meshing/bisect.hpp)
- ZZ tutorial (i-tutorial 1.6, Poisson with H1 order 3). Flux recovery into `HDiv(mesh, order=2)` via `gf_flux.Set(flux)`, with η²_T = ∫_T (1/λ)|λ∇u_h − I_h(λ∇u_h)|². "Mark": `mesh.SetRefinementFlag(el, eta2[el.nr] > 0.25*maxerr)` (vectorised: `eta2.NumPy() > 0.25*maxerr`). Then `mesh.Refine()`. Loop: `while fes.ndof < 50000:`. — [docs/i-tutorials/unit-1.6-adaptivity/adaptivity.ipynb](https://github.com/NGSolve/ngsolve/blob/d242b9b4bbad5617676171d8daf58e13d64fb1ad/docs/i-tutorials/unit-1.6-adaptivity/adaptivity.ipynb) (rendered: https://docu.ngsolve.org/latest/i-tutorials/unit-1.6-adaptivity/adaptivity.html). The older `py_tutorials/adaptive.py` uses the same 0.25·maxerr rule and `while fes.ndof < 100000`. — [py_tutorials/adaptive.py L91-103](https://github.com/NGSolve/ngsolve/blob/d242b9b4bbad5617676171d8daf58e13d64fb1ad/py_tutorials/adaptive.py)
- Maxwell EVP tutorial (2.4.1, Fichera corner). `cube2.edges.hpref=1 # mark edges for geometric refinement`, `mesh.RefineHP(levels=2, factor=0.2)`, `HCurl(mesh, order=3)`, Poisson projection `proj = IdentityMatrix() - gradmat @ invh1 @ gradmattrans @ m.mat`, `solvers.PINVIT(a.mat, m.mat, pre=projpre, num=12, maxit=20)`. The tutorial has no adaptive loop. — [docs/i-tutorials/unit-2.4-Maxwell/Maxwellevp.ipynb](https://github.com/NGSolve/ngsolve/blob/d242b9b4bbad5617676171d8daf58e13d64fb1ad/docs/i-tutorials/unit-2.4-Maxwell/Maxwellevp.ipynb)
- The "wta/adaptivity" tutorial also uses `while fes.ndof < 50000` with NumPy-vectorised marking. — [docs/i-tutorials/wta/adaptivity.ipynb](https://github.com/NGSolve/ngsolve/blob/d242b9b4bbad5617676171d8daf58e13d64fb1ad/docs/i-tutorials/wta/adaptivity.ipynb)

### Inferences
- In NGSolve the stop rule is entirely user code. The official examples use only a DOF budget. They do not stop on an eigenvalue change, an estimator tolerance or a minimum growth.
- Because `Refine` rebuilds curvature itself, an explicit `mesh.Curve(p)` after `Refine` is redundant but harmless. A mesh refined before it was ever curved stays straight until `Curve` is called.
- Projecting boundary midpoints onto CAD can invert thin boundary tets on strongly curved walls. That is why Netgen tracks `quality_loss`. It matches this repo's "repaired by bisection must go through `highorder.single_level`" invariant (AGENTS.md).

### Gaps
- No NGSolve doc page gives an adaptive Maxwell eigenvalue loop or a multi-mode indicator rule.
- I did not check whether `RefineHP` interacts with `Curve`.

## 4. deal.II: KellyErrorEstimator, GridRefinement fixed_number / fixed_fraction, Maxwell eigen tutorials

### Takeaway
deal.II supplies marking helpers. `refine_and_coarsen_fixed_number` takes fractions of cells. `refine_and_coarsen_fixed_fraction` takes fractions of the total error ("bulk criterion or Dörfler marking"), with norm L1 by default. Both accept an optional `max_n_cells` cap. Its Kelly estimator is documented for generalized Poisson problems only. I found no deal.II tutorial for adaptive Maxwell eigenvalue problems. Stop rules are left to the application.

### Cited Findings
- Signatures (deal.II 9.7.0): `refine_and_coarsen_fixed_number(tria, criteria, top_fraction_of_cells, bottom_fraction_of_cells, max_n_cells = numeric_limits<unsigned int>::max())`; `refine_and_coarsen_fixed_fraction(tria, criteria, top_fraction, bottom_fraction, max_n_cells = max(), norm_type = VectorTools::L1_norm)`; `refine_and_coarsen_optimize(tria, criteria, order = 2)`. Fixed fraction is "Also known as the bulk criterion or Dörfler marking". Guidance: "setting top_fraction_of_cells to 1/3 will result in approximately doubling the number of cells in two dimensions … The same effect in three dimensions is achieved by refining 1/7th of the cells." — [deal.II GridRefinement namespace](https://dealii.org/current/doxygen/deal.II/namespaceGridRefinement.html)
- Kelly: the jump of a·∂u_h/∂n over faces, with face factor `cell_diameter_over_24` (original, h_K/24), `face_diameter_over_twice_max_degree` (h_F/(2p_F)) or `cell_diameter`. The docs warn "the estimate is not to be trusted" as a true a posteriori bound, and say it targets −∇·a∇u = f. The page does not mention FE_Nedelec/H(curl). — [deal.II KellyErrorEstimator](https://dealii.org/current/doxygen/deal.II/classKellyErrorEstimator.html)
- The closest deal.II Maxwell work is on Nédélec elements on locally refined meshes with hanging nodes, for the time-harmonic (source) problem. It is not an eigenproblem. — Kinnewig, Wick, Beuchler, ACM TOMS (2025), per search result [deepdyve listing](https://www.deepdyve.com/browse/journals/0098-3500)
- Theory reference: Boffi & Gastaldi prove "optimal convergence of a standard adaptive scheme based on edge finite elements for the Maxwell eigenvalue problem". — [arXiv:1804.02377](https://arxiv.org/abs/1804.02377)

### Inferences
- In deal.II tutorials a loop usually runs a fixed number of cycles, which is the common deal.II pattern, but I did not verify a specific Maxwell example. Typical fixed_number fractions such as 0.3/0.03 appear in tutorials, but they are not on this page, so I do not cite them.

### Gaps
- No deal.II tutorial or code-gallery program combining FE_Nedelec, an eigenvalue solve and AMR was found.
- I did not read the estimator and θ of Boffi-Gastaldi (only the abstract was reachable).

## 5. ACE3P / Omega3P (SLAC)

### Takeaway
Omega3P's published AMR (SLAC–RPI, 2004) used a ZZ recovery estimator on E, H or their gradients, element-integrated. Elements are marked against a threshold, and a size field is optimised to minimise element count subject to the error. RPI mesh modification (refine, coarsen, smooth) keeps curved boundaries "properly approximated" against the 3D geometry model. The adaptive loop stops when the total error δ = Σ η_i falls below a specified value, so the stop is an estimator threshold. Convergence was judged by plotting frequency and Q against unknowns per AMR step, and against measurement. Omega3P uses tetrahedral elements with basis functions up to 6th order. I found no public p-adaptive stop rule.

### Cited Findings
- "Omega3P belongs to a suite of codes … based on tetrahedral mesh and finite element basis functions up to 6th order." Its design target was "frequency accuracy of 0.01%" (NLC requirement). — [Ge et al., SLAC-PUB-10496 / OSTI 827003, CEFC 2004](https://www.osti.gov/servlets/purl/827003) (PDF text read)
- Estimator: "the Zienkiewicz-Zhu (ZZ) method is used as the error estimator … err = ‖E_raw − E_rec‖_L2, err = ‖H_raw − H_rec‖_L2, or err = ‖∇E_raw − ∇E_rec‖_L2, err = ‖∇H_raw − ∇H_rec‖_L2 … we integrate over each element to get an error for that element. For a given threshold, we judge which elements need to be refined or coarsened. The refine-coarsen process will be stopped if the total error δ is less than a specified value where δ = ∫ η dΩ = Σ η_i." — same source
- Mesh adaptation: "a mesh size field is generated by performing an optimization that minimizes the total number of elements in the whole domain subject to a constraint set by the local error field and size field … RPI's mesh modification package … can effectively modify the starting mesh until the target element size and shape distribution are met with the curved domain boundaries properly approximated." — same source
- Results: the Trispal 2-cell cavity gave frequency and Q convergence vs unknowns per refinement step (Fig. 2). Table I: π mode measurement 1064 MHz / Q 11340; UMR 1066 / 12111; AMR 1066 / 12004. ΔQ/Q: −22.5 % measured, −19.6 % UMR, −21.7 % AMR. For the NLC DDS cell, "an order of magnitude reduction" in DOFs vs uniform refinement. — same source
- Later SLAC summary: AMR on the RIA RFQ used about 0.4 M DOFs, about 10× fewer than uniform refinement for the same accuracy, and "unstructured grids, third-order elements and AMR" gave frequency and Q accuracy better than standard codes. — [SLAC-PUB-11914](https://www.slac.stanford.edu/pubs/slacpubs/11750/slac-pub-11914.pdf) (summary via search; PDF returned 503)
- Omega3P documentation says 2nd order is usually enough ("For most applications, using 2nd order is good enough to obtain the solution accuracy") and allows per-region order and curved surfaces. — [Omega3P Top-Level Commands (CW23)](https://s3df.slac.stanford.edu/people/cho/cw23/commands/omega3p-commands.docx) (search snippet only; fetch failed with a TLS error / 503)
- A 2016 SCOREC report covers "Improvements in Curved Mesh Adaptation Procedure for the Omega3P Code" (in-memory integration, load balancing, adaptive loop, higher-order geometry). — [SCOREC report 705](https://scorec.rpi.edu/reports/view_report.php?id=705) (title via search; the page fetched as the generic homepage)
- A JLab benchmark comparing codes ran Omega3P on 2 mm 10-node (curved quadratic) tets with eigen-residual < 1e-7, and HFSS with "adaptive passes with 0.01% max frequency change per pass". — [Tian et al., PAC09 TH5PFP093](https://accelconf.web.cern.ch/pac2009/papers/th5pfp093.pdf) (from this repo's earlier CST notes)

### Inferences
- Omega3P practice: users judge convergence from the sequence of frequency and Q (wall loss) per refinement, together with a total-estimator threshold. The 2004 paper does not mention a "consecutive passes" rule.
- The "curved elements up to order 6" in the task brief matches "basis functions up to 6th order". The geometric order of Omega3P meshes in that work was quadratic (10-node tets, per the PAC09 benchmark). I found no source for 6th-order geometry.

### Gaps
- The current ACE3P user documentation (order and p-refinement commands, any automatic p-refinement stop rule) was not reachable: the SLAC docx/PDFs returned TLS errors or 503.
- I found no public source on whether Omega3P does automatic p-refinement or what tolerance it uses.

## 6. CST Studio Suite eigenmode solver (tetrahedral)

### Takeaway
CST's eigenmode AMR is h-refinement of the tetrahedral mesh. It stops when the largest eigenfrequency change between successive passes (ΔF) falls below the user's accuracy value. Minimum passes always run, and maximum passes caps the run. The FEM eigenmode solver has curved tets of user-selectable order with "True Geometry Approximation", and solver order 1-3 (2nd is the default per old help text). Numeric defaults for ΔF and the pass counts could not be read from primary sources.

### Cited Findings
- CAS 2023 tutorial: "the refinement will increase the mesh density in, e.g. high field areas until the variation in resonance frequency of the Eigenmodes is less than the error value given". 1D Results > "Adaptive Meshing" shows the frequency and tets per pass. — [CERN CAS 2023, M. Wendt](https://indico.cern.ch/event/1294829/contributions/5442426/attachments/2698007/4683942/CAS2023_simulations_wCover.pdf) (from this repo's earlier CST notes, `research_notes/CST eigenmode çözücüsü analizi/tet_fem_eigensolver.md`)
- CST 2013 help (search summary only, mirror unreachable): ΔF is the largest eigenfrequency change between two successive passes, set by "Accuracy". Minimum passes are always run, maximum passes caps the run. The first mesh comes from the automatic "expert system". — [mweda CST2013 help mirror](http://www.mweda.com/cst/cst2013/mergedprojects/cst_microwave_studio/special_solvopt/special_solvopt_mesh_adaption_properties_sap.htm) (503 on 2026-10-26)
- CST 2024: Eigenmode solver "multilevel mesh refinement option to force stronger refinement in the first passes". — [GoEngineer, CST 2024 What's New](https://www.goengineer.com/blog/simulia-cst-studio-suite-2024-whats-new)
- Curved elements: "curved elements of arbitrary order" in the FEM eigenmode solver since MWS 2011 SP3, with "True Geometry Approximation". — [Microwave Journal 2011](https://www.microwavejournal.com/articles/14593-cst-introduces-curved-finite-element-for-eigenmode-solver-in-cst-microwave-studio-2011). 2012 slide: "Curved tetrahedral mesh available (up to 3rd order)". — [ICAP2012 MOAAI2](https://epaper.kek.jp/ICAP2012/talks/moaai2_talk.pdf). Published runs: solver order 3 "(constant)", curved "up to order 5 (user defined)", accuracy 1e-12 (MWS 2018). — [arXiv:2001.09686](https://arxiv.org/pdf/2001.09686)

### Inferences
- CST stops on the change between passes, with min/max pass counts. I found no documented "N consecutive converged passes" or minimum-growth setting. The 2024 "multilevel" option suggests early passes may otherwise grow too little.

### Gaps
- Default ΔF, default min/max passes, refinement fraction per pass, and any "check N passes" option: not found in reachable primary sources. The "check frequency for N passes" in the brief could not be confirmed.

## 7. ANSYS HFSS eigenmode

### Takeaway
HFSS eigenmode adaptive meshing stops on the **change in each mode's frequency between consecutive passes** ("Maximum Delta Freq. Per Pass", in percent). It must hold for "Minimum Converged Passes" consecutive passes, after at least "Minimum Number of Passes", and within "Maximum Number of Passes". Each pass refines a fixed percentage of the worst tets ("Percent Refinement", default 30 %), which guarantees mesh growth. This is the only code here with both a consecutive-pass count and a forced minimum growth per pass.

### Cited Findings
- PyAEDT eigenmode setup template (mirrors the AEDT setup keys): `"NumModes": 1, "MaxDeltaFreq": 10, "ConvergeOnRealFreq": False, "MaximumPasses": 3, "MinimumPasses": 1, "MinimumConvergedPasses": 1, "PercentRefinement": 30, "BasisOrder": 1, "DoLambdaRefine": True, "DoMaterialLambda": True, "SetLambdaTarget": False, "Target": 0.2, "UseMaxTetIncrease": False`. The driven template has `"MaxDeltaS": 0.02, "MaximumPasses": 6, "MinimumPasses": 1, "MinimumConvergedPasses": 1, "PercentRefinement": 30`. — [ansys/pyaedt src/ansys/aedt/core/modules/setup_templates.py L102-150 (main, 2026-10-26)](https://github.com/ansys/pyaedt/blob/main/src/ansys/aedt/core/modules/setup_templates.py)
- PyAEDT describes MaxDeltaFreq as the "maximum difference in freq between consecutive passes". — [qiskit-metal pyaedt eigenmode renderer source](https://qiskit.org/documentation/metal/_modules/qiskit_metal/renderers/renderer_ansys_pyaedt/hfss_renderer_eigenmode_aedt.html) (search snippet)
- Qiskit Metal's own HFSS eigenmode defaults: `'max_delta_f': 0.5, 'max_passes': 10, 'min_converged': 1, 'min_passes': 1, 'n_modes': 1, 'pct_refinement': 30, 'basis_order': 1`. These are third-party defaults, not Ansys defaults. — [qiskit_metal.analyses.EigenmodeSim](https://qiskit.org/ecosystem/metal/apidocs/qiskit_metal.analyses.EigenmodeSim.html) (search snippet)
- Ansys training (2020 R2): "After each solution, tetrahedral elements are "graded" for their accuracy to Maxwell's equations. User defines percentage of "bad" tetrahedral elements to be refined after each pass (30% Default)". Adaptive meshing ends when "Convergence is reached (before the Maximum Number of Passes is reached) OR Maximum Number of Passes is reached, but convergence has not been reached". Delta S "Default value of 0.02 is reasonable for most cases" (driven). — [Ansys HFSS GS 2020R2 LE3 FEM MeshSoln](https://innovationspace.ansys.com/courses/wp-content/uploads/2021/07/HFSS_GS_2020R2_EN_LE3_FEM_MeshSoln.pdf) (PDF text read)
- Ansys help 2024 R2: for eigenmode solutions "specify Maximum Delta Frequency Per Pass and, if desired, Converge on Real Frequency Only". The Adaptive Options tab holds "Maximum Refinement Per Pass", "Maximum Refinement", "Minimum Number of Passes", "Minimum Number of Converged Passes". — [Setting Adaptive Analysis Parameters for HFSS (v242)](https://ansyshelp.ansys.com/public/Views/Secured/Electronics/v242/en/Subsystems/HFSS/Content/HFSS/SettingAdaptiveAnalysisParametersforHFSS.htm). Eigenmode setup (2025 R1): "enter 2 or more passes" for adaptive analysis. — [Adding an Eigenmode Solution Setup (v251)](https://ansyshelp.ansys.com/public/Views/Secured/Electronics/v251/en/Subsystems/HFSS/Content/HFSS/AddinganEigenmodeSetup.htm)
- Ansys help (search summary): "if the Maximum Delta Frequency Per Pass criteria is achieved in addition to any specified expression convergence criteria, the adaptive analysis stops. Otherwise, the solution continues until the requested number of passes is completed". An older Ansoft eigenmode guide describes the test as the change in the computed frequency of each eigenmode from one pass to the next, with an example of 0.1 %. — [Specifying Expressions for Adaptive Convergence](https://ansyshelp.ansys.com/public/Views/Secured/Electronics/v242/en/Subsystems/HFSS/Content/HFSS/SpecifyingExpressionsforAdaptiveConvergence.htm); [Ansoft eigenmode Getting Started (csus mirror)](https://athena.ecs.csus.edu/~milica/EEE211/PROJ/eigengsg.pdf) (both via search summary; direct fetch 503)
- Community practice: set minimum converged passes to 1 and raise refinement per pass from 20 % to 30 % for simple problems (forum). One tutorial sets max delta frequency to 0 and runs all passes, then judges frequency/Q per pass by hand. — [edaboard](https://edaboard.com/posts/105237); [Ozen coax-resonator video](https://www.ozeninc.com/videos/XjJqcZVe6ig/coaxial-resonator-eigenmode-analysis-in-hfss/) (search summary)
- Benchmark use: "adaptive passes with 0.01% max frequency change per pass" for SRF-type sphere benchmarks. — [PAC09 TH5PFP093](https://accelconf.web.cern.ch/pac2009/papers/th5pfp093.pdf)

### Inferences
- The PyAEDT value `MaxDeltaFreq: 10` is presumably 10 % and matches what users report as the GUI default. It is far too loose for cavities, where 0.01-0.1 % is used in practice. The unit is percent per the help label "(%)" in the brief and the 0.1 % example, but I could not read it from an official page.
- The "Minimum Converged Passes" plus fixed "Percent Refinement" combination guards against both failure modes asked about: a lucky single pass, and a pass that does not change the mesh.

### Gaps
- Official Ansys eigenmode defaults (GUI) could not be read: help pages give names, not values. The PyAEDT template values are the best proxy and may differ from the GUI.
- Curvilinear element defaults for eigenmode ("Apply curvilinear elements") were not checked.

## 8. COMSOL RF Module: eigenfrequency adaptation

### Takeaway
COMSOL's "Adaptive Mesh Refinement (Stationary and Eigenvalue Adaptation)" uses **all eigenmodes by default** (Solution selection "All", weights 1). The default adaptation method is longest-edge bisection, with alternatives regular refinement, general modification and "Rebuild mesh" (remeshing). Element selection defaults are "Rough global minimum" ×1.7 growth, or 0.5 fractions. In 3D the default is only **1 adaptation** (10 when goal-oriented termination is Auto). The cap is 10 M elements.

### Cited Findings
- Defaults (COMSOL 6.3 and 6.4 identical): Solution selection "Use last" except "Eigenvalue studies default to All"; Weights default 1 "on all solutions (eigenmodes)". Adaptation method: General modification / Rebuild mesh / Regular refinement ("bisects all edges") / Longest edge refinement (default). Allow coarsening: max coarsening factor 5 (general modification) or 3 (rebuild). "Maximum number of refinements" default 5 (not with rebuild). Element selection: "Rough global minimum" with element count growth factor 1.7 ("about 70% more elements"); "Fraction of worst error" 0.5; "Fraction of elements" 0.5. Maximum number of elements 10,000,000; adaptation stops if exceeded. "Maximum number of adaptations: Default 5 in 1D, 2 in 2D, and 1 in 3D. With Goal-oriented termination set to Auto, the defaults are 20 (1D), 15 (2D), and 10 (3D)." Advanced: "Use classic method for vector elements" restores pre-6.1 behaviour. — [COMSOL 6.3 ref](https://doc.comsol.com/6.3/doc/com.comsol.help.comsol/comsol_ref_solver.36.157.html); [COMSOL 6.4 ref](https://doc.comsol.com/6.4/doc/com.comsol.help.comsol/comsol_ref_solver.36.160.html)

### Inferences
- COMSOL's default is a fixed number of adaptations (a pass budget) with forced growth per pass (×1.7). Goal-oriented termination adds a convergence stop. The adaptation keeps CAD conformity through the mesh sequence (refine or rebuild), but I did not confirm this on the page.

### Gaps
- The error-estimate form for vector (curl) elements, and the goal-oriented termination tolerance and its quantity (eigenvalue change?), were not on these pages.

## 9. SuperLANS / SLANS / Superfish (2D axisymmetric) accuracy practice

### Takeaway
These 2D codes have no automatic adaptive loop of the kind above. Accuracy is managed by mesh density, and high-order elements are the main lever. SUPERLANS uses biquadratic (8-node isoparametric) quadrilaterals and claims better accuracy than Superfish's finite-difference triangles at the same mesh size. Superfish users run mesh-size studies; one published case says a finer mesh "does not change results".

### Cited Findings
- "SUPERLANS uses the finite element method of calculation and a mesh with quadrilateral biquadratic elements in contrast to the finite difference method and triangular mesh used by SUPERFISH … the finite element method gives better accuracy with the same mesh size or similar accuracy with a more coarse mesh." — [Cornell SuperLANS guide SRFD960814-09](https://www.classe.cornell.edu/rsrc/Home/Research/SRF/SuperLANS/SRFD960814-09.pdf) (search summary)
- CERN CAS lecture lists SuperLANS as "FEM version of Superfish" and warns of systematic boundary errors from meshing. — [Jensen, CAS 2010 numerical](https://cas.web.cern.ch/sites/default/files/lectures/ebeltoft-2010/jensen-numerical.pdf) (search summary)
- Practice example: SUPERFISH mesh step 2.5 mm, "finer mesh does not change results", used as an exact axisymmetric reference for 3D codes. — this repo's earlier notes (`accuracy_benchmarks.md` L64), source cited there.

### Gaps
- Superfish's built-in accuracy checks were not looked up (I believe it reports an estimated frequency error, but have no source).

## 10. Cross-code: who stops on the change between passes, who guards against no-growth or lucky passes, who uses an estimator threshold?

### Takeaway
- **Stop on the change between passes:** HFSS (ΔF per mode, %, with min passes, min *converged* passes and max passes) and CST (max ΔF over modes, with min/max passes).
- **Stop on an estimator threshold:** Palace (`Tol` on the energy-normalised ZZ norm, plus MaxIts/MaxSize), Omega3P 2004 (total ZZ error δ below a value), and MFEM `ThresholdRefiner` (`total_err_goal`, default 0, i.e. effectively off).
- **Stop on a budget only:** NGSolve tutorials (ndof), MFEM examples and miniapps (max DOFs or iterations), COMSOL default (number of adaptations, unless goal-oriented termination is on), deal.II (user loop).
- **Explicit consecutive-converged-pass guard:** only HFSS ("Minimum Converged Passes", default 1 in the PyAEDT template, so even HFSS does not require two by default).
- **Minimum growth per pass:** HFSS ("Percent Refinement" 30 % of tets) and COMSOL ("Rough global minimum" ×1.7) force growth. Dörfler (Palace θ = 0.7) and max-fraction marking (MFEM 0.5, NGSolve 0.25) always mark at least one element, so they grow, but they do not guarantee a minimum growth rate. No code was found that rejects or extends a pass whose element count barely changes.

### Cited Findings
- HFSS: [PyAEDT setup_templates.py](https://github.com/ansys/pyaedt/blob/main/src/ansys/aedt/core/modules/setup_templates.py); [Ansys GS 2020R2](https://innovationspace.ansys.com/courses/wp-content/uploads/2021/07/HFSS_GS_2020R2_EN_LE3_FEM_MeshSoln.pdf)
- CST: [CAS 2023](https://indico.cern.ch/event/1294829/contributions/5442426/attachments/2698007/4683942/CAS2023_simulations_wCover.pdf)
- Palace: [basesolver.cpp L215-387](https://github.com/awslabs/palace/blob/8bd206f7e10e5a2ec93a2483514894d14c8a5102/palace/drivers/basesolver.cpp#L215-L387)
- MFEM: [mesh_operators.cpp](https://github.com/mfem/mfem/blob/master/mesh/mesh_operators.cpp)
- NGSolve: [adaptivity.ipynb](https://github.com/NGSolve/ngsolve/blob/d242b9b4bbad5617676171d8daf58e13d64fb1ad/docs/i-tutorials/unit-1.6-adaptivity/adaptivity.ipynb)
- COMSOL: [6.4 ref](https://doc.comsol.com/6.4/doc/com.comsol.help.comsol/comsol_ref_solver.36.160.html)
- Omega3P: [OSTI 827003](https://www.osti.gov/servlets/purl/827003)

### Inferences
- For several modes: Palace takes the RMS of the per-mode normalised indicators for marking. COMSOL weights all modes equally (weights 1). HFSS and CST check every mode's frequency change, taking the max over modes. Omega3P 2004 shows per-mode (π mode) convergence. No code was found that marks on the max over modes.
- For this project (curved p3 labels): a combined rule matches industry practice. Stop on relative Δf of every tracked mode below tol for ≥ 2 consecutive passes (HFSS-style). Require a minimum growth per pass (HFSS 30 % / COMSOL 1.7× style). Keep a DOF/element cap (all codes). Optionally add an energy-normalised estimator floor (Palace-style). Mark with Dörfler θ ≈ 0.5-0.7 on the RMS-over-modes indicator (Palace). This is a synthesis, not something any single code documents.

### Gaps
- No primary-source numeric defaults for CST ΔF and pass counts, or for HFSS GUI eigenmode defaults (only PyAEDT proxies).
- No public description of the HFSS or CST element-selection indicator ("graded for their accuracy to Maxwell's equations" is the only Ansys statement).
